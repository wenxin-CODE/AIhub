# 深空航行自主任务管理 Agent：原型开发规划

> 版本：1.0\
> 项目定位：面向商业航天求职展示的可运行 Agent 原型\
> 核心场景：模拟地球至火星巡航期间的航天器状态监测、异常诊断、任务重规划与人工审批\
> 安全边界：仅用于仿真、教学和软件能力展示，不连接真实航天器，不生成可直接下发真实飞行器的控制指令。

------------------------------------------------------------------------

## 1. 项目概述

### 1.1 项目背景

深空航行期间，航天器会持续产生能源、热控、推进、姿态、通信等子系统遥测数据。地球与航天器之间存在通信延迟，地面团队无法对所有异常进行实时干预。因此，航天任务需要具备一定程度的自主状态监测、故障分析、任务规划和异常恢复能力。

本项目开发一个以大语言模型 Agent
为任务交互与编排核心、以确定性算法和仿真工具为事实计算基础的深空航行自主任务管理系统。系统接收模拟遥测数据，识别异常，检索设备知识，调用诊断和资源评估工具，形成可解释的处置建议，并在人工批准后更新仿真任务计划。

### 1.2 项目目标

交付一个可本地运行、可现场演示的 Web 原型，证明以下能力：

1.  **任务理解**：理解用户提出的航行任务目标、状态查询和异常处置需求。
2.  **遥测监测**：接收、解析和展示模拟遥测数据，识别阈值越界、趋势异常和数据质量问题。
3.  **故障诊断**：结合多参数关联、规则、故障知识库和 LLM
    推理，输出候选故障及证据。
4.  **工具调用**：按需调用遥测分析、故障规则、能源预算、任务调度等工具。
5.  **任务重规划**：在能源、时间、设备和任务优先级约束下生成备选计划。
6.  **人机协同**：对高影响操作设置审批关口，记录审批、执行模拟结果和审计日志。
7.  **可解释性**：展示数据依据、规则依据、工具结果、方案取舍和不确定性。

### 1.3 非目标

首版不实现以下能力：

-   不控制真实航天器、火箭、发动机或推进系统。
-   不实现真实飞行级 GNC、姿态控制或闭环制导。
-   不宣称完成真实火星轨道设计、再入或着陆控制。
-   不把 LLM 输出直接视为遥测事实、故障结论或安全控制指令。
-   不以"多 Agent 数量"作为项目亮点；优先保证流程可靠、结果可复现。

### 1.4 建议演示主线

**场景：地火巡航期间出现能源异常。**

初始任务计划要求维持通信、热控、导航和科学载荷运行。仿真遥测显示太阳能输入功率持续下降、电池荷电状态下降、某载荷功耗偏高。Agent
需要：

1.  获取最新遥测与历史趋势。
2.  判断数据是否完整、是否存在异常。
3.  识别受影响的子系统并形成候选原因。
4.  检索相关设备手册和故障处置知识。
5.  调用能源预算工具，评估剩余能源与安全储备。
6.  生成多个任务调整方案并比较影响。
7.  提交人工审批。
8.  审批通过后，在仿真环境中应用新计划。
9.  读取后续遥测，验证是否恢复到预期状态。

该场景能够集中展示 Agent
的状态理解、工具调用、多轮推理、RAG、结构化输出、人工介入和闭环验证。

## 3. 产品需求文档（PRD）

### 3.1 用户角色

  角色                  主要需求
  --------------------- --------------------------------------------
  任务控制人员          查看航天器状态、理解告警、审查诊断和计划
  任务规划人员          查看任务约束、比较备选计划、批准计划变更
  系统管理员/演示人员   配置仿真场景、注入故障、重置任务和查看日志

### 3.2 核心功能范围

#### 功能 A：任务态势总览

-   展示当前任务阶段、任务时间、通信状态和总体健康状态。
-   展示能源、热控、推进、姿态、通信等子系统状态。
-   展示关键遥测指标的当前值、单位、阈值和趋势。
-   展示告警列表、告警等级、发生时间和处理状态。
-   支持查看遥测历史曲线和单条数据详情。

**验收标准：**
用户能够从总览页面识别当前任务状态、主要异常和受影响子系统；数据带时间戳、单位和数据质量标记。

#### 功能 B：遥测数据接入与异常检测

-   支持仿真数据持续生成和历史数据回放。
-   对遥测数据进行字段校验、单位校验、时间戳校验和缺失值标记。
-   支持固定阈值、变化率和持续时间规则。
-   对重复、乱序、过期和缺失数据进行处理。
-   区分"异常告警"和"数据质量告警"。

**验收标准：**
注入预设异常后，系统能够在设定的处理周期内生成对应告警；过期或缺失数据不会被误当作最新有效状态。

#### 功能 C：Agent 故障诊断

-   用户可以通过自然语言询问异常原因。
-   Agent 自动获取相关遥测、告警和历史趋势。
-   Agent 调用规则诊断工具，形成候选故障。
-   Agent 检索航天设备知识库，补充故障机理和处置依据。
-   输出候选原因、支持证据、反证/未知信息、影响范围和置信度。
-   允许用户追问诊断过程或要求补充证据。

**验收标准：**
对预设能源故障场景，系统能够引用实际遥测值和工具结果，不得只根据 LLM
自由生成结论。

#### 功能 D：任务重规划与方案评估

-   根据当前能源预算、任务优先级、设备状态和任务依赖生成备选方案。
-   支持暂停低优先级科学载荷、调整非关键任务频率等仿真操作。
-   计算每个方案的预计能源消耗、能源余量和任务影响。
-   设置硬约束，例如关键通信、热控和最低能源储备不得被违反。
-   比较方案优缺点并说明推荐理由。

**验收标准：**
方案必须通过确定性约束校验；违反硬约束的方案应被拒绝或明确标记为不可执行，不能由
LLM 自行宣布可行。

#### 功能 E：人工审批与仿真执行

-   对任务计划变更创建审批单。
-   展示变更前后任务计划、影响分析和风险。
-   支持批准、拒绝和要求重新规划。
-   只有批准后才允许在仿真器中应用变更。
-   记录审批人、时间、方案版本、工具调用和执行结果。
-   支持执行后验证与失败回滚/重新规划。

**验收标准：** 未审批的计划不得改变仿真任务状态；每次变更均可追踪。

#### 功能 F：任务报告与审计

-   生成任务状态摘要、异常诊断报告和计划变更报告。
-   保存关键输入、工具输出、模型输出、审批和执行记录。
-   支持按任务、时间和告警查询历史记录。

**验收标准：**
能够从一份报告追溯到对应遥测、规则、知识来源、方案和审批记录。

### 3.3 首版明确不做

-   真实航天器数据接入。
-   真实遥控指令生成和下发。
-   实时轨道控制或发动机控制。
-   真实飞行级故障诊断认证。
-   全面覆盖所有航天器子系统。
-   复杂的多航天器协同和火星地面资源生产。

## 4. 典型业务流程

### 4.1 主流程：能源异常诊断与任务重规划

1.  仿真器生成正常遥测。
2.  场景注入器逐步降低太阳能输入功率，并模拟某载荷功耗升高。
3.  数据接入模块校验数据并写入时序记录。
4.  规则检测模块产生能源异常告警。
5.  Agent 接收告警事件，读取当前状态和相关历史数据。
6.  Agent 调用能源诊断工具，获取候选故障及证据。
7.  Agent 检索设备手册、故障案例和处置规则。
8.  Agent 汇总诊断结果，并标明不确定性。
9.  Agent 调用任务规划工具生成多个候选计划。
10. 约束校验器检查关键任务、能源储备和任务依赖。
11. Agent 生成方案比较报告并发起人工审批。
12. 用户批准后，仿真执行器更新任务计划。
13. 仿真器生成后续遥测，系统验证能源趋势和任务状态。
14. 若未达到预期，Agent
    重新诊断和规划；若达到预期，则关闭告警并归档报告。

### 4.2 异常分支

-   **数据不完整：**
    暂停诊断结论，标记数据质量问题，等待新数据或请求人工检查。
-   **原因不确定：**
    输出多个候选原因和需要补充的观测，不强行给出唯一结论。
-   **无可行计划：**
    保留当前安全状态，升级人工处理，不生成虚假的可行方案。
-   **审批拒绝：** 保持原计划，记录拒绝原因。
-   **执行失败：**
    不假设执行成功；读取仿真器状态，恢复到已知状态或进入人工处理流程。
-   **工具超时/失败：** 重试策略受限，记录错误并降级为只读分析。

## 5. Agent 与系统架构

### 5.1 架构原则

采用"单一任务编排 Agent + 确定性领域工具 + 可选专业子 Agent"的渐进架构。

首版不建议一开始就拆成大量自治 Agent。多 Agent
会增加状态同步、调试、成本和不可预测性。先把一个可观测、可测试的
LangGraph 工作流做可靠，再按职责拆分。

### 5.2 逻辑架构

``` text

  ├── 方案比较与人工审批
  └── 执行记录与审计

后端 API
  ├── 任务与场景管理
  ├── 遥测数据接入
  ├── 告警与事件管理
  ├── Agent 工作流接口
  └── 审批与仿真执行接口

  ├── 意图识别 / 任务路由
  ├── 状态获取
  ├── 数据质量检查
  ├── 异常分析
  ├── 知识检索
  ├── 诊断汇总
  ├── 任务方案生成
  ├── 约束校验
  ├── 人工审批节点

```

### 5.5 LangGraph 状态设计

建议使用结构化 State，而不是把所有信息都塞进对话历史。

``` python
from typing import TypedDict, Optional, List, Dict, Any

class MissionState(TypedDict, total=False):
    mission_id: str
    scenario_id: str
    user_request: str

    mission_status: Dict[str, Any]
    telemetry: List[Dict[str, Any]]
    data_quality: Dict[str, Any]
    alerts: List[Dict[str, Any]]

    diagnosis: Dict[str, Any]
    evidence: List[Dict[str, Any]]
    retrieved_docs: List[Dict[str, Any]]

    candidate_plans: List[Dict[str, Any]]
    selected_plan: Optional[Dict[str, Any]]
    constraint_result: Dict[str, Any]

    approval_status: str
    execution_result: Dict[str, Any]
    verification_result: Dict[str, Any]

    messages: List[Any]
    errors: List[Dict[str, Any]]
```

实施要求：

-   每个节点只负责清晰的一类工作。
-   工具输入输出采用 Pydantic 等结构化 Schema。
-   关键节点记录耗时、输入摘要、输出和错误。
-   对审批节点使用 LangGraph interrupt/checkpoint 等机制实现暂停和恢复。
-   恢复时从持久化 checkpoint 继续，避免重复执行已完成的外部副作用。
-   对仿真执行使用幂等请求 ID，防止恢复时重复应用计划。

## 6. 数据设计与仿真场景

### 6.1 首版子系统范围

建议只模拟五类子系统，避免范围失控：

1.  能源系统：太阳能输入功率、电池荷电状态、电池温度、总负载功率。
2.  热控系统：设备温度、舱内温度、散热器状态。
3.  推进系统：推进剂余量、储箱压力、推进系统可用状态。
4.  姿态系统：姿态误差、角速度、姿态控制设备状态。
5.  通信系统：链路状态、信号质量、最近通信时间、数据延迟。

首个主场景聚焦能源异常，其余子系统用于展示关联影响和后续扩展。

### 6.2 遥测数据结构示例

``` json
{
  "mission_id": "MARS-CRUISE-001",
  "timestamp": "2031-08-18T12:00:00Z",
  "subsystem": "power",
  "parameter": "battery_soc",
  "value": 62.5,
  "unit": "%",
  "quality": "VALID",
  "source": "simulator",
  "sequence": 10241
}
```

建议字段：

-   mission_id：任务标识。
-   timestamp：采集时间，统一使用 UTC 存储。
-   subsystem：所属子系统。
-   parameter：参数名称。
-   value / unit：数值和单位。
-   quality：VALID、MISSING、STALE、SUSPECT 等质量状态。
-   source：数据来源。
-   sequence：序列号，用于识别重复或乱序数据。

### 6.3 故障场景设计

  -------------------------------------------------------------------------------------------
  场景                    注入方式                 预期系统行为
  ----------------------- ------------------------ ------------------------------------------
  能源输入下降            太阳能功率逐步下降       趋势告警、能源诊断、任务降载建议

  负载异常升高            某科学载荷功耗持续偏高   关联分析、负载识别、任务调整

  电池温度升高            温度超过告警阈值         热控风险提示、限制相关操作

  遥测数据中断            停止发送部分参数         数据质量告警，不使用过期值做确定性诊断

  传感器异常              单个传感器跳变或卡死     识别传感器异常候选，不直接判定设备故障

  通信延迟                延迟或乱序投递数据       显示数据时效性，避免将旧数据当作当前状态
  -------------------------------------------------------------------------------------------

### 6.4 最小知识库

首版知识库只需围绕演示场景构建：

-   航天器能源系统组成和基本原理。
-   太阳能阵列、电池和电源管理单元的功能。
-   电池温度、荷电状态、功率等参数说明。
-   能源系统常见故障模式。
-   FMEA 示例和故障处置流程。
-   任务负载优先级和安全约束。
-   数据字典、告警规则和仿真场景说明。

每个文档片段应保留来源、标题、版本、章节和适用范围。Agent
引用知识时展示来源，避免把检索内容误当作真实遥测数据。

## 7. 核心工具设计

工具是 Agent
与航天业务系统交互的边界。工具应输入明确、输出结构化、结果可测试。

  ---------------------------------------------------------------------------------------
  工具名称                    主要输入                     主要输出
  --------------------------- ---------------------------- ------------------------------
  `get_mission_status`        mission_id                   任务阶段、任务状态、更新时间

  `query_telemetry`           mission_id、参数、时间范围   遥测序列、单位、质量标记

  `detect_anomalies`          遥测序列、规则配置           告警列表、异常区间

  `diagnose_power_fault`      告警、能源遥测               候选原因、证据、置信度

  `search_technical_docs`     查询文本、子系统             文档片段、来源元数据

  `calculate_energy_budget`   电源输入、负载、容量、时长   能源预测、剩余量、储备

  `generate_task_plans`       当前计划、任务优先级、约束   多个候选计划

  `validate_task_plan`        候选计划、硬约束             可行性、违反项

  `submit_approval`           方案 ID、变更摘要            审批单 ID、状态

  `apply_simulated_plan`      已批准方案 ID                仿真执行结果

  `verify_mission_state`      预期状态、最新遥测           验证结果、偏差
  ---------------------------------------------------------------------------------------

### 7.1 工具设计要求

-   所有参数使用明确类型和单位。
-   对数值设置合理范围校验。
-   关键工具返回 `status`、`data`、`reason`、`timestamp`。
-   工具失败时返回可处理错误，不用自然语言伪装成功。
-   工具结果是事实来源，LLM 只能解释和组织，不能篡改。
-   计划生成与计划执行分离。
-   约束校验器必须独立于 LLM。
-   执行工具必须校验审批状态、方案版本和幂等键。

### 7.2 能源预算工具示例

首版可以使用简化模型：

``` text
净功率 = 发电功率 - 总负载功率

预测能源变化 = 净功率 × 时间

预测电池能量 = 当前电池能量 + 预测能源变化
```

实际实现必须统一
W、Wh、小时等单位，并考虑充放电效率、容量上限、最低安全储备和模型适用范围。该简化模型仅用于原型演示，不代表真实航天器电源系统模型。

### 7.3 任务规划工具示例

任务可定义为：

``` json
{
  "task_id": "SCIENCE-03",
  "name": "科学载荷实验",
  "priority": 2,
  "power_w": 180,
  "duration_hours": 2,
  "mandatory": false,
  "dependencies": []
}
```

规划目标可以是：在满足硬约束的前提下，最大化任务价值，同时控制能源消耗和计划变更数量。

硬约束示例：

-   关键通信任务不得被关闭。
-   热控最低运行要求必须满足。
-   预测能源不得低于安全储备。
-   有依赖关系的任务必须满足先后顺序。
-   未经审批不得应用任务计划变更。

## 8. 技术选型

建议以 Python 作为 Agent
和仿真核心语言，前端与数据服务按团队熟悉程度选择。

  层次         推荐方案          说明
  ------------ ----------------- ----------------------------------------
  Agent 编排   LangGraph         状态图、条件路由、checkpoint、人工审批
  LLM          GPT 或 DeepSeek   意图理解、诊断解释、方案说明
  结构化输出   Pydantic          工具参数、诊断和计划 Schema
  后端 API     FastAPI           提供任务、遥测、Agent、审批接口
  数据库       MySQL             任务、告警、审批和审计记录
  向量检索     Chroma            技术手册和故障案例 RAG
  数据处理     Pandas / NumPy    遥测清洗、趋势计算和统计分析
  前端         React             态势总览、曲线、对话、审批页面
  图表         ECharts           遥测趋势和能源预测
  测试         pytest            工具、工作流和场景测试
  部署         Docker Compose    本地一键启动和演示

### 8.1 模型使用原则

-   LLM 负责理解请求、选择工具、整合证据和解释方案。
-   确定性 Python 工具负责单位换算、阈值判断、能源预算和约束验证。
-   RAG 负责检索设备手册、术语和故障案例。
-   不让 LLM 凭空生成遥测值、轨道参数或设备阈值。
-   重要结论必须给出数据来源、计算结果或文档依据。

## 10. 开发流程与里程碑

建议按 6 个阶段推进。单人开发可按约 4--6
周安排，具体取决于前端完成度、模型接入和仿真深度。

### 阶段 1：业务学习与需求冻结（约 3--5 天）

工作内容：

-   学习航天器子系统、深空巡航、遥测/遥控。
-   学习 FDIR、FMEA 和任务规划基础。
-   确定能源异常为首个演示场景。
-   完成 PRD、流程图、状态机和数据字典。
-   明确所有数值是仿真参数，不冒充真实航天器数据。

交付物：

-   项目需求文档。
-   业务流程图。
-   遥测数据字典。
-   首版故障场景说明。

完成标准：能够不看资料讲清楚主场景的业务逻辑和 Agent 的职责边界。

### 阶段 2：仿真数据与领域工具（约 4--6 天）

工作内容：

-   设计正常遥测数据集。
-   编写遥测生成器和故障注入器。
-   实现数据清洗、质量检查和阈值检测。
-   实现能源预算计算。
-   实现故障规则诊断。
-   实现任务计划生成和硬约束校验。

交付物：

-   可回放的遥测数据集。
-   至少 4 种故障注入场景。
-   可独立测试的领域工具。
-   工具输入输出 Schema。

完成标准：不调用 LLM，也能稳定检测预设异常、计算能源预算并校验计划。

### 阶段 3：Agent 工作流与 RAG（约 5--7 天）

工作内容：

-   建立 LangGraph State。
-   实现意图路由和状态查询。
-   接入遥测、诊断、知识检索和能源工具。
-   建立能源系统知识库。
-   实现结构化诊断报告。
-   实现候选计划生成和方案解释。
-   加入超时、重试、错误处理和日志。

交付物：

-   可运行的 LangGraph 工作流。
-   工具调用记录。
-   带来源的 RAG 检索结果。
-   结构化诊断和规划结果。

完成标准：Agent
能够针对能源异常自主调用多个工具，输出有证据的诊断和方案。

### 阶段 4：审批、checkpoint 与闭环仿真（约 4--5 天）

工作内容：

-   增加人工审批节点。
-   持久化 LangGraph checkpoint。
-   实现批准、拒绝和恢复执行。
-   实现仿真任务计划应用。
-   实现执行后状态验证。
-   增加幂等处理和审计记录。

交付物：

-   人工审批流程。
-   可恢复的工作流。
-   仿真执行器。
-   执行结果和审计记录。

完成标准：未审批不能执行；审批后能应用仿真计划；中断恢复不重复执行已完成副作用。

### 阶段 5：Web 展示与集成（约 5--7 天）

-   展示诊断证据和知识来源。
-   展示多方案对比和人工审批。

交付物：

-   可操作的 Web Demo。
-   一键启动配置。
-   演示数据和场景重置功能。

## 11. 测试方案与验收标准

### 11.1 功能验收用例

  编号   测试场景                     预期结果
  ------ ---------------------------- ------------------------------------
  T01    正常遥测输入                 系统展示正常状态，不产生错误告警
  T02    太阳能功率持续下降           触发能源异常告警
  T03    电池荷电状态下降且负载升高   诊断工具识别关联证据
  T04    单个传感器数值跳变           标记可疑数据，不直接判定设备故障
  T05    遥测数据过期                 标记 STALE，不当作当前状态
  T06    检索能源系统手册             返回相关片段和来源
  T07    生成降载计划                 返回多个结构化候选方案
  T08    计划违反关键通信约束         约束校验拒绝该方案
  T09    用户拒绝审批                 原计划保持不变
  T10    用户批准计划                 仿真器应用新计划并记录日志
  T11    执行后能源仍持续下降         验证失败，触发重新诊断或人工升级
  T12    工作流中断后恢复             从 checkpoint 恢复，不重复应用计划

### 11.2 质量指标

首版建议关注：

-   异常检测：预设场景的检测结果是否正确。
-   诊断可追溯性：每个诊断结论是否有遥测或知识依据。
-   约束正确性：违反硬约束的计划是否全部被拦截。
-   审批安全性：未审批方案是否无法执行。
-   工作流可靠性：失败、重试和恢复是否符合预期。
-   响应性能：记录各工具和工作流节点耗时。
-   演示稳定性：相同场景可重复得到可解释结果。

不要在缺少测试数据时宣称"诊断准确率
99%"或"达到航天级可靠性"。先建立有标签的仿真测试集，再报告准确率、召回率、误报率和漏报率。

### 11.3 安全要求

-   所有数据页面明确标注"仿真数据"。
-   Agent 不能直接调用真实遥控接口。
-   计划生成与计划执行严格分离。
-   关键任务和最低安全储备是硬约束。
-   人工审批是执行前置条件。
-   对模型幻觉、工具失败、数据过期和权限不足设置降级路径。
-   记录模型版本、提示词版本、工具版本和关键输入输出，便于复现。

## 12. Demo 展示脚本

建议控制在 5 分钟左右。

### 第 1 步：展示任务态势（约 30 秒）

介绍飞船处于地火巡航阶段，当前能源、热控、推进、姿态和通信系统状态正常。

### 第 2 步：注入异常（约 30 秒）

点击"注入能源异常"，模拟太阳能输入功率下降和科学载荷功耗升高。

展示遥测曲线变化和系统告警。

### 第 3 步：Agent 自主诊断（约 90 秒）

向 Agent 提问：

> 飞船当前出现了什么异常？请分析可能原因，并说明判断依据。

展示 Agent：

-   查询遥测。
-   分析趋势。
-   调用故障诊断工具。
-   检索能源系统知识库。
-   输出候选原因、证据和不确定性。

### 第 4 步：生成任务调整方案（约 90 秒）

向 Agent 提问：

> 在保障关键通信、热控和最低能源储备的前提下，重新规划当前任务，给出至少两个备选方案并比较影响。

展示能源预算、候选计划和硬约束校验结果。

### 第 5 步：人工审批与执行反馈（约 60 秒）

选择一个方案并批准。

展示仿真器更新任务计划、生成后续遥测、验证执行效果，并形成任务报告。

## 13. 面试讲解框架

### 13.1 1 分钟项目介绍

"我开发的是一个面向深空巡航场景的自主任务管理 Agent
原型。项目主要解决航天器在长距离巡航过程中，地面控制存在通信延迟、遥测数据量大、异常分析和任务调整依赖人工等问题。

系统以 LangGraph
编排任务流程，接入模拟遥测数据，通过规则和趋势分析发现异常，再结合 RAG
知识库和故障诊断工具分析可能原因。针对能源异常，Agent
会调用能源预算和任务规划工具生成多个备选方案，并通过独立约束校验器检查关键任务和能源储备。最终由人工审批后，在仿真环境中执行计划并验证结果。

项目重点不是让大模型直接控制航天器，而是让大模型承担任务理解、工具编排、证据整合和决策辅助工作，将确定性计算与安全校验交给专业工具。"

### 13.2 高频追问准备

**业务与航天知识**

1.  为什么深空航行需要自主任务管理？
2.  遥测和遥控有什么区别？
3.  飞船巡航期间需要监控哪些子系统？
4.  深空通信延迟会带来什么影响？
5.  FDIR 的检测、隔离和恢复分别是什么？
6.  为什么能源异常可能影响通信、热控和导航？

**Agent 与系统设计**

1.  为什么选择 LangGraph，而不是简单的 Agent 循环？
2.  为什么使用状态图？State 中保存哪些信息？
3.  如何避免 Agent 重复调用工具？
4.  如何处理工具调用失败和工作流中断？
5.  为什么采用 RAG？知识库如何切分和更新？
6.  如何让诊断结果有证据、可追溯？
7.  为什么不把所有逻辑都交给 LLM？
8.  多 Agent 是否必要？如何判断拆分边界？

**数据与算法**

1.  如何模拟遥测数据？
2.  如何识别趋势异常？
3.  如何区分传感器故障和设备故障？
4.  如何计算能源预算？
5.  如何处理缺失、乱序和延迟数据？
6.  如何评估故障诊断效果？

**安全与可靠性**

1.  如果 Agent 给出错误诊断怎么办？
2.  如何避免不合理的任务计划？
3.  为什么需要硬约束校验？
4.  人工审批如何实现？
5.  checkpoint 恢复时如何避免重复执行？
6.  如果仿真执行后状态没有改善怎么办？
7.  这个原型距离真实航天任务系统还差什么？

### 13.3 面试表达边界

应准确区分：

-   已实现：本项目代码实际具备的功能。
-   已仿真：在模拟数据和模拟任务环境中验证的功能。
-   理论设计：依据公开航天资料设计，但尚未实现或验证的能力。
-   真实航天应用：需要专业模型、硬件在环测试、独立安全验证和航天工程认证。

## 15. 风险与应对

  -----------------------------------------------------------------------------------------
  风险                    影响                         应对
  ----------------------- ---------------------------- ------------------------------------
  航天知识范围过大        学习和开发周期失控           只聚焦深空巡航和能源异常

  遥测数据缺乏            Agent 无法展示真实分析过程   自建带标签的仿真数据集

  LLM 输出不稳定          诊断和计划结果不一致         结构化输出、确定性工具和规则校验

  多 Agent 过度设计       调试和状态管理复杂           首版单图编排，按需拆分

  任务规划不可信          生成违反安全约束的方案       硬约束独立校验，人工审批

  RAG 检索质量差          错误依据影响诊断             维护小而准确的领域知识库，保留来源

  Demo 依赖外部模型服务   网络或额度问题导致无法演示   准备缓存结果或可切换模型配置

  被误解为真实飞控系统    项目可信度和安全边界不清     全程标注仿真，明确非飞行控制用途
  -----------------------------------------------------------------------------------------

## 17. 开发完成的判定标准

项目达到以下条件，即具备较好的求职展示价值：

1.  面试官能够通过界面看到一艘处于深空巡航阶段的仿真航天器。
2.  能够注入能源异常，并看到遥测变化和告警。
3.  Agent 能够自主查询数据、调用诊断工具和检索技术资料。
4.  Agent 能够输出带证据的故障分析，而不是只生成一段解释性文字。
5.  Agent 能够调用能源预算和任务规划工具生成备选方案。
6.  独立校验器能够拒绝违反硬约束的方案。
7.  人工批准前，仿真任务计划不会被修改。
8.  批准后能够执行仿真计划，并根据后续数据验证结果。
9.  工作流能够记录过程，并支持必要的中断恢复。
10. 开发者能够解释每个模块的输入、输出、职责、失败处理和安全边界。

**最终定位：**
这是一个以深空巡航能源异常为切入点，融合航天领域知识、遥测数据分析、FDIR、任务规划、RAG、工具调用和人工审批的自主任务管理
Agent
原型。项目的核心竞争力不是"接入了一个大模型"，而是形成了一个有数据、有工具、有约束、有审批、有反馈、可追溯的任务决策闭环。
