## 1. 项目定位

**名称**：星枢 StarOps — Satellite Mission Planning & Intelligence Agent
**宣传语**：让 Agent 理解卫星任务，让算法辅助航天决策。

**背景**：商业航天对地观测业务中，观测任务规划与 SAR 影像处理都需要专业人员配合专用软件完成。本项目用 LLM Agent 把自然语言需求转为结构化任务，用确定性工具完成计算与校验，人工审批后执行。

**项目边界（必须写进 README 和演示口播）**：
- 观测窗口、卫星状态均为**明确标注的模拟数据**，不宣称真实卫星实时调度能力。
- 基础条纹/斑点检测**不等同于** ScanSAR 扇贝效应识别算法；普通滤波不冒充 CycleGAN。
- 不实现真实卫星遥控、任务下发、轨道控制与资源预约。
- 影像分析结果不作为真实航天任务决策依据。
- **当前交付的是"遥感影像处理"与"业务流程治理"，不是"遥感智能解译"**：不做地物分类、目标检测、异常检测等解译能力，也不宣称已解决 AI 解译结果的可信度问题。
- 审批关口解决的是**操作治理与流程可追溯**，不构成对遥感算法科学正确性的证明。

### 1.1 业务问题定义（对外论证的唯一口径）

> **证据分级纪律**：所有对外表述必须区分三类信息——
> ① **行业事实**（有文献、专利、官方文档或标准可溯源）→ 可直接引用；
> ② **技术原理推导**（由原理推出，但未经本项目实测）→ 必须标注为推断；
> ③ **项目价值主张**（本项目做了什么、边界在哪）→ 由代码与测试自证。
> 找不到可溯源来源的统计数字，**一律不进文档、不进口播**。

本项目只认领三个与已实现功能对得上的业务问题：

| # | 业务问题 | 业务表现 | StarOps 的解决思路 | 与当前实现匹配度 |
|---|---|---|---|---|
| **痛点一** | **卫星任务规划复杂** | 多颗卫星、多种载荷、多批次任务之间存在时间、空间与资源约束；突发任务到来时还需人工调整既有计划 | 自然语言需求解析 + 卫星资源查询 + 确定性约束校验 + 多目标排序 + 人工审批 | **高**（规则较简单，真实业务约束待补） |
| **痛点二** | **遥感数据处理专业门槛高** | 原始遥感数据需经多环节预处理与质量检查；SAR 的处理参数与算子选择直接影响噪声抑制、边缘保留与辐射信息 | SAR 元数据解析 + 算法工具调用 + 多管线横评 + 质量指标评估 + 处理报告 | **高**（横评已跑通，真实数据链路待补） |
| **痛点三** | **遥感业务流程缺乏统一的自动化治理** | 专业人员不仅要出结论，还要审核方案、确认执行条件、追踪过程并担责；单一算法工具无法覆盖完整流程 | Agent 工作流编排 + 人工审批 + 状态持久化 + 异常恢复 + 全流程审计 | **高**（安全闭环已跑通） |

三者构成递进闭环：**卫星资源如何合理使用 → 遥感数据如何有效处理 → 专业工具如何融入实际业务流程**。

**痛点三的准确表述**（不得夸大为"AI 结论不敢交付"）：遥感数据处理结果**缺少标准化的质量评价、处理过程追溯与人工复核机制**。解译类风险（分类错误、目标漏检、置信度不足、模型泛化不足）属于另一条业务线，本项目不认领。

### 1.2 两类业务的边界（避免概念混用）

| 业务类型 | 主要风险 | 本项目是否覆盖 |
|---|---|---|
| 遥感**影像处理** | 数据质量、定标精度、几何精度、滤波造成的信息损失 | ✅ 覆盖（阶段③） |
| 遥感**智能解译** | 分类错误、目标漏检、置信度不足、模型泛化能力不足 | ❌ 不覆盖（明确划出边界） |

### 1.3 观测规划 vs 数传规划（概念区分）

二者相关但不同，复杂星座规划需处理二者的耦合：

| 规划类型 | 主要解决的问题 |
|---|---|
| **观测任务规划** | 哪颗卫星、什么时候、对哪个区域、采用什么载荷进行观测 |
| **数传任务规划** | 观测数据什么时候、通过哪个地面站、以什么资源配置完成下传 |

本项目 MVP 只做**观测任务规划**，数传规划列为进阶项。

| # | 能力 | 落点 |
|---|---|---|
| 1 | 任务理解 | LLM 把自然语言转结构化约束（区域/时间/分辨率/成像模式/优先级） |

| 8 | **业务约束真实度**（阶段②补） | 侧摆角/姿态机动、能源、存储容量、载荷工作模式、地面站可见窗口逐步接入校验器 |

- 不让 LLM 自行计算过境时间、分辨率、评分或图像指标。
- **不做遥感智能解译**（地物分类、目标检测、异常检测），不把影像处理包装成解译能力。
- 不宣称已接入真实卫星测运控系统、实时轨道数据与任务下发接口，因此不宣称已解决完整的应急响应链路。
- 不把项目自设的工程阈值（如辐射强度守门）包装成行业标准。

            ▼
FastAPI
  ├── 任务 API        ├── Agent 工作流 API
  ├── 审批 API        ├── 执行 API（校验幂等键 + 审批状态）
  └── 审计查询 API
            ▼
LangGraph 三链编排
  ├── 观测规划 Agent：需求解析 → 卫星查询 → 窗口查询 → 硬约束校验 → 评分排序 → 审批关口 → 落库 → 验证

            ▼
Tools 层（确定性 + 可测试）
  ├── 卫星资源 / 观测窗口 / 约束校验 / 方案评分
  ├── 三阶段调度内核（order_scheduling.py：AS/VS/ES + CV + PM）

  └── 审批提交 / 计划执行（幂等） / 状态验证

### 3.2 核心原则（面试可背）

1. **单一编排图优先**：两个 Agent 各自一张状态图，不做多 Agent 自由协作 —— 状态同步、调试、成本都不可控。
2. **LLM 只编排不算**：理解、决策、组织输出归 LLM；数值计算与约束判定归 Python 工具。
3. **生成与执行分离**：规划 Agent 产出"待审批方案"，执行接口必须校验审批状态、方案版本、幂等键。
4. **约束校验器独立于 LLM**：校验器是纯代码，不是提示词约束。
5. **工具结果是事实来源**：LLM 只能解释和组织，不能篡改。

### 3.3 LangGraph 状态

```python
class PlanningState(TypedDict, total=False):
    task_id: str
    user_request: str
    task_type: str                       # planning | sar
    # 需求与数据
    task_requirements: Dict[str, Any]    # 区域/时间窗/分辨率/模式/优先级
    candidates: List[Dict[str, Any]]     # 候选卫星
    windows: List[Dict[str, Any]]         # 候选观测窗口
    data_quality: Dict[str, Any]         # FRESH/STALE/EXPIRED/SUSPECT
    # 规划与校验
    scored_plans: List[Dict[str, Any]]
    constraint_result: Dict[str, Any]    # 通过/拒绝 + 违反项
    # 审批与执行
    approval_id: Optional[str]
    approval_status: str                 # pending/approved/rejected
    plan_version: int
    idempotency_key: str
    execution_result: Dict[str, Any]
    verification_result: Dict[str, Any]
    # 通用
    retrieved_docs: List[Dict[str, Any]]
    evidence: List[Dict[str, Any]]
    messages: List[Any]
    errors: List[Dict[str, Any]]
```

**实施要求**
- 每节点只做一类事；工具出入参用 Pydantic Schema。
- 关键节点记录耗时、输入摘要、输出、错误。
- 审批节点用 LangGraph `interrupt` + checkpoint 暂停/恢复。
- 恢复时从持久化 checkpoint 继续，**不重复执行已完成副作用**。
- 执行类工具必须校验审批状态 + 方案版本 + 幂等键。

## 4. 核心功能模块

### 4.1 模块一：卫星遥感观测任务规划 Agent

**输入**：自然语言需求。

> 规划一次北京区域的遥感观测任务，未来 3 天内完成，要求空间分辨率优于 2 米，优先光学卫星。

**参数抽取**（缺失必问，禁止自行假设）：

| 参数 | 示例 | 缺失策略 |
|---|---|---|
| 观测区域 | 北京 | 必问（区域名 or 几何） |
| 时间范围 | 未来 3 天 | 必问 |
| 卫星类型 | 光学 | 默认光学，提示 |
| 空间分辨率 | 优于 2 米 | 必问 |
| 成像模式 | 多光谱 | 可默认 |
| 优先级 / 目标 | 尽早完成、高 | 可默认 |

**工作流**：需求解析 → 卫星资源查询 → 观测窗口查询 → **硬约束校验** → 方案评分排序 → **生成待审批方案** → **人工审批关口** → 写入任务计划 → 结果验证 → 报告

**硬约束（独立校验器执行）**：
- 空间分辨率 ≤ 用户阈值
- 成像模式匹配
- 观测窗口未过期（`data_quality != EXPIRED`）
- 模拟云量 ≤ 阈值
- 入射角在有效区间
- 任务优先级不冲突
- **未审批不得写入任务计划**

**真实业务约束（阶段②逐步接入，当前为手写确定性规则）**：

| 约束族 | 具体约束 | 当前状态 |
|---|---|---|
| 成像几何 | 侧摆角范围、姿态机动能力、立体/同轨要求 | 待补（模拟数据字段已预留） |
| 平台资源 | 星上能源、存储容量、载荷工作模式、任务时长 | 待补 |
| 地面段 | 地面站可见窗口、数传带宽与优先级 | 待补（数传规划列为进阶项） |
| 时间与覆盖 | 轨道过境时刻、目标区域可见性、重访周期 | 待补（当前用预生成窗口近似） |
| 环境 | 云量、天气、太阳高度角与光照条件 | 部分（云量模拟） |

> 当前手写规则可以证明 **Agent 能解析约束并调用规划工具**，但**不能证明规划结果符合真实卫星运行条件**。阶段②需至少完成一组有实际物理意义的约束校验（侧摆角 + 载荷模式 + 存储余量优先），再谈"规划引擎"。

**评分算法**（Python，多目标排序）：分辨率得分、时间紧迫度得分、云量得分、入射角得分、优先级加成 → 加权归一化排序。权重来自"推荐算法排序优化"经验。

**工具表**：

| Tool | 输入 | 输出 |
|---|---|---|
| `query_satellites` | 类型、分辨率上限、成像模式 | 卫星列表 |
| `query_observation_windows` | 卫星 ID、区域、时间范围 | 候选窗口 + 数据质量标记 |
| `validate_constraints` | 任务参数、候选窗口 | 校验结果 + 违反项 |

### 4.2 模块二：SAR 遥感影像智能分析 Agent

**输入**：SAR 影像文件 + 自然语言分析需求。

> 分析这张影像是否存在明显斑点噪声和条纹效应，并给出处理建议。

**工作流**：影像读取 → 质量检测 → 问题诊断 → 处理选型 → **工具可用性校验** → **人工审批关口** → 执行处理 → 前后对比 → 报告生成

**质量指标**：灰度分布、局部方差、噪声估计值、等效视数 ENL、条纹强度、PSNR/SSIM（有参考时）。

**处理选型：双层基线 + 深度模型**

处理算子分三层，构成**可对比的递进基线**：

| 层 | 算子 | 定位 | 优先级 |
|---|---|---|---|
| L1 经典基线 | 中值滤波 / Lee 滤波 / 自适应滤波 / FANS（邻域） | **纯 numpy 实现，零外部依赖**，作为对照组 | **P0** |
| L2 深度基线 | **GeomaticsAndRS/sar 预训练残差 CNN**（详见 §4.3） | 公开预训练权重，验证"学习先验"相对经典滤波的增益 | P2（后置于 §4.4 真实数据链路） |
| L3 专项增强 | ScanSAR 扇贝效应抑制（专利方向） | 进阶项，MVP 不做 | P2 |

**关键设计**：三层跑**同一套指标**。只有 L2 能在统一指标下证明优于 L1，Agent 才有理由推荐它；否则 Agent 应回退到 L1。**DL 不是默认选项，是被评测选出来的选项。**

**算法层不依赖图像库**：L1 的全部算子（局部方差、ENL、Lee / 中值 / 自适应滤波、FFT 条纹检测、PSNR / SSIM）用纯 numpy 实现（积分图 + 滑窗 + FFT），图像读写自带 PNG 编解码（zlib + struct）。OpenCV 仅作为"读 TIFF / GeoTIFF"的可选增强，缺失时演示链路与全部指标计算不受影响。这带来两个好处：**指标计算不被重依赖卡住**，且 **L1 与 L2 天然共用同一套指标口径**——这正是横评可信的前提。

**辐射强度守门（项目自设工程阈值，不是行业标准）**：候选管线中值偏移超过 5% 的直接淘汰并记录原因。中值滤波对乘性斑点有系统性下偏（gamma(2,0.5) 的中位数约为均值的 69%），会把辐射强度拉低约 13%。**降噪不能以破坏辐射强度为代价**——这是 SAR 影像可用于定量反演的前提。

**阈值口径必须写清（否则 5% 只是一个看起来专业的数字）**：

| 口径项 | 本项目定义 | 理由 |
|---|---|---|
| 比较量纲 | **线性强度**（DN / 灰度域），不用 dB | dB 对数压缩后偏移量纲不可比 |
| 统计范围 | **全图均值**，排除四周 2 像素边界 | 边界填充方式会污染均值 |
| 低信噪比区域 | 局部方差接近噪声底的像元参与统计但**单独标注** | 避免噪声底像素稀释偏移量 |
| 超阈容差 | 单像元超 5% 不淘汰，**整体均值**超 5% 才淘汰 | 防止个别强散射点误杀整条管线 |
| 阈值性质 | 工程验收阈值，用于让横评可**自动裁决** | 不对外宣称是行业公认安全线 |

> 该阈值的意义是**让"降噪效果"与"辐射保真"之间有一个可自动裁决的平衡点**，而不是宣称 5% 就是行业标准。真实定量产品还需配合 §4.4 的辐射定标链路校验 σ⁰ 量级。

**区分可视化处理与定量分析**：同一处理链路的输出，用途不同则要求不同——可视化与目视判读允许为观感调整，**定量产品（后向散射系数反演、变化检测、定标）不得为了视觉效果改变数据**。因此守门只对"定量意图"生效，处理策略按应用目标选择，并在处理报告中标注该影像属于哪一类用途。

**SAR 处理链路的行业事实对齐**：斑点滤波在 ESA SNAP / NASA 的官方流程中是**按应用选择的可选步骤**，不是所有场景的固定环节；辐射定标才是定量分析的前置。因此本项目不把"滤波"当成处理链路的必然终点，而是把它作为"质量评价 + 策略选择"的一个环节。

**条纹单独处理**：SAR 深度学习的公开工作几乎全部集中在斑点去噪，条纹（striping）至今仍以经典频域方法为主（FFT 谱峰检测 → notch filter）。因此 `detect_striping` 保持**经典实现**，不硬上深度学习。强度用**峰值突出度**衡量而非"峰值/总能量"，后者会被自然纹理的宽频能量稀释，失去判别力。

**工具表**：

### 4.3 深度去噪模型接入：GeomaticsAndRS/sar

**是什么**
一个公开的学习型 SAR 去噪模型实现（Learned SAR Speckle Filter，基于深度残差 CNN）。论文思路是利用 Noise2Noise / Noise2Void 范式——**SAR 影像不存在无噪真值**，所以网络只用含噪输入就能训练去噪。作者已对比 Lee 与 BM3D 滤波，结论是 CNN 在效果上相当、在**处理效率上显著优于**传统滤波。

- 仓库：`github.com/GeomaticsAndRS/sar`
- 许可：LGPL-3.0
- 权重：仓库内已附带预训练权重，随仓库下载即可用，**无需自行训练**

**为什么选它（而不是其他开源模型）**

| 候选 | 不选的理由 |
|---|---|
| hi-paris/deepdespeckling (MERLIN/SAR2SAR) | 质量高，但吃复数 SLC（.cos/.npy），与本项目 PNG/JPG/TIFF 的演示链路不匹配，格式转换成本高 |
| JK-the-Ko/SAR-CAM | 官方实现但**无预训练权重**，需自己训，2 周周期内不现实 |
| CL-SAR-Despeckling / Practical-SAR-Despeckling-Codes | 适合进阶做评测与对比研究，BasicSR 依赖重，不适合进 MVP 主链路 |
| **GeomaticsAndRS/sar** | **自带权重 + 直接吃 TIFF + 有 sample.tif 可即刻演示** |

**接入方式：推理代码内联，不 fork 整个工程**

仓库本身是研究代码，不适合整仓引入。采取**只取权重 + 最小推理封装**：

```
data/models/sar_drn/
├── weights/           # 从仓库下载的预训练权重
├── inference.py       # 最小推理封装（自写，~100 行）
│   ├── load_model()           # 加载权重，构建推理图
│   ├── to_intensity()        # 原始 SAR → 强度图
│   ├── batch_predict()       # 分块推理（stride 可配）
│   └── postprocess()         # 合并 patch、均值修正
└── README.md          # 权重来源、许可、版本
```

**管线对照**

| 环节 | 经典基线（L1） | 深度基线（L2） |
|---|---|---|
| 输入 | 强度图 uint8/float32 | 强度图，需补齐 2 通道（VH/VV） |
| 处理 | OpenCV 滤波算子 | 分块 CNN 推理（stride 128，可配） |
| 参数 | 窗口大小、sigma | 权重版本、mean_correction（smart/always/never）、stride |
| 输出 | 处理后影像 | 处理后影像 + 推理元数据（耗时、权重版本、patch 数） |
| 依赖 | OpenCV | PyTorch（推理即可，CPU 可跑） |

**通道数适配（必须处理的坑）**
该模型训练时使用 **2 通道强度图**（VH + VV 双极化）。演示用的单通道影像需要复制为双通道再推理，输出取回单通道。这是要在工具层显式封装的一步，不能指望模型自动兼容。

**推理封装接口约定**

```python
# 工具层调用形态
result = apply_dl_despeckle(
    image_path="sample.tif",
    model="sar_drn_v1",
    mean_correction="smart",
    stride=128,
)
# 返回：{output_path, elapsed_ms, model_version, weight_source, patch_count, channel_mode}
```

**工程约束（与安全闭环一致）**

1. **模型是工具，不是 Agent**：LLM 只决定"是否调用 DL 算子、用哪组参数"，推理由封装完成，模型输出不被 LLM 改写。
2. **权重可溯**：工具返回 `model_version` 与 `weight_source`，写入 `tool_execution` 表，可复现。
3. **失败降级**：权重缺失、PyTorch 不可用或推理异常 → 自动回退 L1 经典滤波，并在结果中标注"DL 不可用，已降级"，**不伪装成功**。
4. **离线可演示**：权重随仓库本地化，演示不依赖外网下载。
5. **许可合规**：LGPL-3.0，源码修改与分发方式在 README 注明；本项目只调用不修改，符合 LGPL 要求。

**评测口径**

同一张图、同一套指标，三条管线横评：

| 指标 | 说明 | 无参考 |
|---|---|---|
| 局部方差 / CV | 斑点强度 | ✅ |
| ENL 等效视数 | 斑点抑制程度 | ✅ |
| 噪声估计值 | 噪声水平 | ✅ |
| PSNR / SSIM | 与参考图对比 | 需要成对数据集（进阶用 CL-SAR-Despeckling） |
| 推理耗时 | 效率对比 | ✅ |

> **表达纪律**：DL 模型的收益只在**同图同指标**下成立。允许说"预训练深度模型在本地样本上优于经典滤波"，不允许说"达到 SOTA"或"航天级去噪"。

**接入工作量**：下载权重 + 写推理封装约 0.5–1 天，不占用主链路工期。

> **优先级说明**：L2 深度模型由 P1 降为 **P2**，先做 §4.4 的真实数据链路。原因见 §4.4。

### 4.4 真实 SAR 数据链路（阶段③ P0，优先级高于 L2 深度模型）

**为什么排在 L2 之前**：能证明"算法管线能跑在真实产品上"，比多一个模型名字更有说服力。合成模拟影像上的横评只能证明管线逻辑正确，**不能证明适用于真实 SAR 产品**。

**目标链路**

```
原始产品（GeoTIFF / SLC / GRD）
  → 元数据解析（尺寸、dtype、位深、地理参考、成像模式）
  → 辐射定标（DN → σ⁰，校验已知地物量级：平静水面通常 -20 ~ -30 dB）
  → 质量指标（CV / ENL / 局部方差 / 条纹）
  → 候选管线横评（按"可视化 / 定量"两种意图分别裁决）
  → 审批关口
  → 执行处理
  → 滤波前后指标对比 + 处理报告
```

**分级实现**

| 级别 | 内容 | 依赖 | 产出 |
|---|---|---|---|
| **P0-a** | 真实 GeoTIFF 读取 + 元数据解析 | rasterio 或 GDAL；缺失时降级为 OpenCV + 外部标定参数 | 真实文件的格式 / 尺寸 / 位深 / 地理参考 |
| **P0-b** | 辐射定标（DN → σ⁰）+ 量级校验 | 定标常数（从元数据或配置文件读取） | σ⁰ 影像 + 水面参考量级校验结果 |
| **P0-c** | 滤波前后指标对比 + 处理报告 | 复用 §4.2 指标层 | 报告：指标表 + 用途定性（可视化/定量）+ 结论 + 已知限制 |
| P1 | σ⁰ / γ⁰ 入射角归一化 | 轨道几何参数 | 归一化后对比度更可解释 |
| P2 | 与开源标准对接（STAC 元数据、openEO 处理后端） | STAC / openEO client | 目录化产物 + 可复现处理链 |

**验收口径**

- 真实 GeoTIFF 的指标与 PNG 解码路径**逐位一致**（跨路径一致性已有回归测试，需补一份真实样本）。
- 辐射定标后，平静水面区域 σ⁰ 应落在 -20 ~ -30 dB；超出即判定定标链路有误，**不允许靠调参掩盖**。
- 处理报告必须包含：输入元数据、用途定性、处理前后指标表、结论、**已知限制**（例如未做地形校正、未做入射角归一化时，**不可用于跨轨道定量比较**）。

**方法摘要（据摘要与图注）**

论文把 EOSTSP（对地观测卫星任务调度，NP-Hard）从"单体式调度问题"重构为**实时订单履约过程**：每个观测任务视为一个独立 order，按顺序处理，每个 order 依次穿过三个专门决策阶段。

| 论文组件 | 职责（据 Fig.2 / Fig.6 图注） |
|---|---|
| **Stage 1 · AS** | Assigning Satellite agent —— 为订单指派卫星 |
| **Stage 2 · VS** | Valid Time Window agent —— 选择有效时窗 VTW |
| **Stage 3 · ES** | Exact Scheduling agent —— 确定精确观测时刻 |
| **CV** | Constraint Verifier —— 分阶段约束检查（staged constraint checking），结合实时场景信息验证可行性 |
| **PM** | Performance Manager —— 迭代校验每个 agent 的决策，失败则触发重规划 |
| **MS** | 失败尝试记忆（failed attempts） |
| **K** | 知识库，保存最终确认的调度计划 |

论文声明：常规场景较 SOTA 提升 4.58%、应急场景提升 13.38%（该数字为论文自身结论，**本项目不引用、不复现**）。

#### 4.5.1 逐项匹配度对比

| 对比维度 | 论文（TSLC / EOSTSP） | 本项目（StarOps） | 匹配度 |
|---|---|---|---|
| **任务目标** | 多订单在线调度，最大化订单利润（profit）的全局可行计划 | 需求驱动的可行性优先 + 效用排序，且**必须过人工审批** | 🟡 **方法论一致、目标不同**。论文是自动求解全局最优，本项目是辅助决策 + 人工把关。本项目的审批关口是论文没有的**更强**约束 |
| **输入数据** | 订单集合（目标点、分辨率、云量、优先级、profit）+ 卫星资源 + VTW + 转移时间矩阵；规模几十至上百星、80–540 单 | 模拟 8 星 / 48 窗口 / 6 区域；需求由自然语言解析 | 🟡 **数据结构同构、规模不可比**。卫星×窗口×约束字段可直接映射；规模差 1–2 个数量级，**不能声称复现论文指标** |
| **调度对象** | **三元**调度：卫星-任务-时间（AS→VS→ES 连续三次决策），产出计划表 | 原为**二元**：卫星-窗口配对，一次性打分排序，**无精确观测时刻** | 🔴 **原架构不匹配**。缺第三阶段（ES），窗口是整段而非可切分 VTW |
| **约束条件** | 分辨率、云量、入射角、VTW 有效期、**姿态转移时间**、**单星单任务资源独占**、利润阈值 | 原仅 6 条单方案独立过滤规则；**无转移时间、无资源独占、无跨订单耦合** | 🔴 **原架构缺关键约束**。这是原架构无法处理多订单的根本原因（单方案独立过滤天然看不到跨方案冲突） |
| **评价指标** | Solution Quality / Objective Function / Constraint Violation / Computation Time / 可行调度率 / token 成本 / atomic chat 成功率；对比 CP、GA、SA、DRL、双层优化等基线 | 原仅单一加权评分（0–1），无约束违反计数、无计算时间对比、无优化算法基线 | 🔴 **原架构缺基准层**。没有基线就无法量化"算法好不好"，这正是 §12.2 里"没有融合传统规划算法"的暴露面 |
| **代码结构** | 单图多智能体，逐单子流程 + PM/CV 校验 + MS/K 记忆 | 单链 DAG：route→parse→query→validate→score→report→approval，**一条链处理一个需求** | 🔴 **原架构是单链**，无法承载"每单独立走三阶段" |

#### 4.5.2 明确结论

**部分匹配，不能原样引入，但可迁移骨架已落地。**

- **可迁移并已引入**：订单驱动抽象（订单队列 → 逐单处理）、三阶段序列决策骨架（AS/VS/ES）、分阶段约束校验（CV）、迭代验证与重规划（PM）、失败记忆（MS）与确认计划知识库（K）、资源独占与姿态转移时间约束、归一化多目标评分。
- **不可直接引入（原因见 §4.5.3）**：论文的全局利润最优目标、真实规模在线调度、LLM token 成本模型、SOTA 基线对比实验结论。
- **结论的可辩护表述**：本项目**吸收了 TSLC 的"订单驱动 + 三阶段 + 外部校验"方法骨架**，把单需求候选排序升级为**多订单可解释调度**；**不复现论文的性能数字，也不宣称等效于论文系统**。

#### 4.5.3 不可直接引入的部分与原因

| 论文要素 | 不可直接引入的原因 | 本项目的处理 |
|---|---|---|
| 全局利润最大化目标 | 本项目订单池无真实 profit 语义，且目标是**可行性 + 可解释**而非利润最优 | 保留 priority→profit 映射，效用 = 三阶段分 × 优先级权重，**只做局部排序不做全局最优声明** |
| 几十至上百星、80–540 单规模 | 模拟数据只有 8 星 48 窗口；扩规模会变成造数据不产生价值 | 保持原型规模；**指标只在本规模内自洽**，不与论文规模对比 |
| 真实转移时间矩阵（轨道 + 敏捷机动） | 本项目无轨道数据、无 TLE、无姿态模型 | 每星固定 `transition_time_min` 参数化模拟，**在报告与文档中标注为简化模型** |
| LLM token 成本 / atomic chat 统计 | 本项目无 Key 时走确定性降级，token 统计不成立 | 保留每个 agent 的 prompt 定义（Fig.4 要素）作为编排契约；**统计指标改为"原子决策数"，不统计 token** |
| 4.58% / 13.38% 对 SOTA 的提升结论 | 依赖同等规模实例与 CP/GA/SA/DRL 基线实现，本项目两周工期无法复现 | **不引用该数字**；如需算法质量结论，必须自建小型基线并标注口径 |
| 论文无人工审批关口 | 论文是自动调度到出计划 | 本项目**保留并强化**审批关口：调度计划生成后仍须人工批准才可落库 |

## 5. 安全闭环设计（本次合并的核心增量）

### 5.1 审批关口

| Agent | 审批对象 | 审批动作 | 审批后动作 |
|---|---|---|---|
| 观测规划 | 观测任务方案（含窗口、卫星、评分） | 批准 / 拒绝 / 要求重规划 | 写入任务计划并生成任务单 |
| SAR 分析 | 影像处理管线（含算子与参数） | 批准 / 拒绝 / 要求换参数 | 执行处理并产出对比报告 |

- 审批单独立成表，记录：审批 ID、对象 ID、方案版本、状态、审批人、时间、意见、方案快照。
- **未审批 → 执行接口直接拒绝**，且该拒绝本身也写审计。
- 拒绝时保留原状态，记录拒绝原因，不自动改写方案。

### 5.2 硬约束校验器

- 纯 Python 函数，不接受 LLM 输出作为判定依据。
- 返回结构：`{passed, violations[], checked_rules[], rule_version}`。
- 违反项必须被 Agent 原样呈现，不得弱化为"基本满足"。
- 校验失败 → 工作流**不进入审批**，直接回到生成节点重新规划。

### 5.3 数据质量标记

遥测/时序概念平移到观测窗口数据：

| 标记 | 含义 | 系统行为 |
|---|---|---|
| `FRESH` | 数据新鲜，窗口在未来 | 正常参与排序 |
| `STALE` | 快照过期，需重新查询 | 提示刷新后再决策，不直接用于排序 |
| `EXPIRED` | 过境窗口已过 | 硬性排除，约束校验直接判失败 |
| `SUSPECT` | 来源或数值可疑 | 标记待复核，不做确定性结论 |

> 关键原则：**过期数据不得当作最新有效状态使用**。这是面试中体现"懂工程"的高价值细节。

### 5.4 幂等与恢复

- 执行类工具必须携带 `idempotency_key = hash(task_id + plan_version + normalized_constraints)`。
- 服务端保存幂等键 → 结果映射，重复提交直接返回首次结果，**不重复执行副作用**。
- 审批节点用 LangGraph `interrupt`/`checkpoint`；恢复时从 checkpoint 续跑，已完成节点不重跑。
- checkpoint（工作流状态）与 audit_log（业务审计）**分表管理**，不要混。

### 5.5 审计

双表结构：
- `tool_execution`：工具名、输入摘要、输出摘要、状态、耗时、调用链 ID。
- `audit_log`：操作者、动作、对象 ID、时间、详情。

额外记录：**模型版本、提示词版本、工具版本**，保证可复现。
所有数据页面标注"模拟数据"；敏感配置走环境变量。

### 5.6 降级路径

| 情形 | 系统行为 |
|---|---|
| 数据不足/过期 | 暂停结论，标记数据质量，请求刷新或转人工 |
| 约束无解 | 明确告知无满足全部约束的方案，列出放松了哪些条件，**不生成虚假可行方案** |
| 工具超时/失败 | 有限重试，记录错误，降级为只读分析 |
| 审批拒绝 | 保持原状态，记录原因 |
| 执行后未改善 | 验证失败 → 重新诊断或升级人工，**不假设执行成功** |

| **`schedule_knowledge`** | knowledge_id、order_id、satellite_id、window_id、plan(JSON)、**plan_signature（计划指纹，去重键）**、created_at（K：已确认计划知识库） |

实施注意：时间统一存 UTC，前端按本地时区渲染；观测窗口与卫星表按 `satellite_id + area_id + time_range` 建索引；模拟数据统一带 `source='simulated'` 标记。

**订单驱动调度三张表的分工**（§4.5）：

- `satellite_order` 是**调度对象本体**：一条订单 = 一个独立观测需求，自带优先级→利润映射、最短成像时长、时间范围、区域、分辨率与云量上限。
- `schedule_memory`（MS）记录**每一次失败尝试**：订单、失败阶段、尝试次数、失败原因列表。它是"下次别再犯同样的错"的载体。
- `schedule_knowledge`（K）记录**已确认的可复用计划**：按 `plan_signature`（卫星 | 窗口 | 观测起止时刻）去重，**同一观测计划无论被确认多少次都只保留一条**，重复确认只更新来源订单与确认时间。窗口重建后，指向已消失窗口的失效知识会被自动清理。
- 上述三张表与 `satellite.transition_time_min` / `satellite.min_imaging_duration_min` 共同构成 TSLC 三阶段（AS→VS→ES）所需的**资源独占**与**姿态转移**前提，见 §4.5.3。
- 迁移采用**幂等补列**（`MIGRATIONS` 列表 + `_apply_migrations`），既有 SQLite 文件无需重建即可升级。

**阶段①关键设计决策**

1. **约束校验按方案粒度**：先把卫星 × 窗口配对成候选方案，再逐个方案过规则。避免出现"整体通过却列了几十条无关违规"的矛盾状态。校验结果拆为 `viable_plans` / `rejected_plans`，评分只对 viable 排序。
2. **过期窗口必须被报告**：EXPIRED 窗口不构成可执行方案，但仍进违规清单，不能静默丢弃。
3. **langgraph 缺失可降级**：内置顺序执行器保证依赖不全时演示仍能跑通。
4. **模拟数据重建**：每次启动重置观测窗口，保证演示规模稳定、结果可重复。**补充修正（v1.2）**：原实现用随机 UUID 作窗口 ID、且时间基准取 `datetime.now()`，导致每次重启窗口集全变——"可重复"名不副实，且知识库 K 的计划指纹无法跨重启去重。现改为**窗口 ID 由「卫星 | 区域 | 起始时刻」派生 + 时间基准锚定当日 UTC 零点**，同一天内重启得到完全相同的数据集。

**阶段③关键设计决策**

5. **算法层与图像库解耦**：局部方差、ENL、Lee / 中值 / 自适应滤波、FFT 条纹检测、PSNR / SSIM 全部用**纯 numpy** 实现（`tools/imaging.py`），自带 PNG 编解码（zlib + struct）。OpenCV 降级为"读 TIFF / GeoTIFF"的可选增强。**指标计算不再被重依赖卡住**，且 L1 与 L2 的指标口径天然统一——这正是"同指标横评"的前提。

6. **管线由实测选出，不由 LLM 指定**：候选管线逐条实跑，用统一指标（CV / ENL / 均值偏移）横评后择优。"DL 优于经典基线"这类结论只能由数据得出，不能由设计者宣称。

7. **5% 辐射强度守门**：中值滤波对乘性斑点有系统性下偏（gamma(2,0.5) 的中位数约为均值的 69%），会把均值拉低 12.8%。超过 5% 偏移的管线直接淘汰并记录原因——**降噪不能以破坏辐射强度为代价**。

8. **被拒管线必须带原因**：选型落选、中值被守门拦下、Lee 胜出，理由全部落到 `rejected_pipelines` 并推到前端。"为什么没选它"必须可解释，不能让 Agent 悄悄换方法。

9. **条纹方向按能量落点判定**：水平条纹（图像沿 y 变化）能量落在 `fx=0` 列 → 0°；垂直条纹 → 90°。强度用**峰值突出度**而非"峰值/总能量"，后者会被自然纹理的宽频能量稀释到 0.0035 量级，失去判别力。

10. **零强度与不可判定要区分**：完全均匀图像返回强度 0.0（确实无条纹），计算异常返回 None（无法判定）。两者语义不同，不能混为一谈。

**订单驱动调度（TSLC）关键设计决策**

11. **三阶段是顺序分解，不是三段提示词**：AS → VS → ES 每一阶段的输出都是下一阶段的**结构化输入**（卫星集 → 窗口集 → 精确时刻），阶段之间通过确定性函数传递，而不是靠 LLM 复述上下文。这样任一阶段可单测、可替换。
12. **约束校验器与决策器彻底分离**：`ConstraintVerifier` 是独立于 AS/VS/ES 的第二套实现，对同一批候选做**交叉验证**。校验器不参与决策，只负责否决——避免"自己算的对不对自己说了算"。
13. **资源独占按"星 × 时刻"建占用表**：同星同时刻只允许一个任务，且相邻任务之间必须留出 `transition_time_min`（姿态转移时间）。这是论文方法成立的物理前提，不满足则三阶段退化为普通匹配。
14. **拒绝原因跨尝试累积**：一次调度失败可能经历多轮重规划（PM 换卫星 / 换窗口 / 换时刻），若只保留最后一次原因，真因会被覆盖。因此用 `stage_reasons` 字典按阶段累积，最终取该阶段前 4 条输出。
15. **排除粒度分两级**：AS 阶段排除**整颗卫星**（该星对该订单完全不可行），VS/ES 阶段只排除**该窗口**（该窗口内找不到可行时刻，但同一星的其他窗口仍可用）。早期版本在 ES 失败时排除整星，会误杀可排期订单。
16. **不适用 ≠ 违规**：区域不匹配的窗口在"云量超限"这类**数值约束**原因之后排序，且单列为"不适用"静默跳过。原因是数值约束类才是真正的决策阻塞点，被大量不适用项淹没会让拒绝原因失去诊断价值。
17. **PM 迭代有上限**（`max_replans=3`）：失败时先写 MS（失败尝试记忆）再换策略重试；超过上限仍不可行则**带根因拒绝该订单**，不无限重试、不静默丢弃——订单被拒必须让用户看见。
18. **利润是优先级到效用的映射，不是真实现金流**：`PRIORITY_PROFIT` 是项目自设的固定映射表，用途是让多订单排队有可比较的效用值。它**不是**论文里的全局利润最大化模型，论文追求全局最优，本项目逐单贪心（见 §4.5.3）。
19. **审批关口保留，论文没有**：TSLC 论文的三阶段是"LLM 直接决策 → 执行"，本项目在其后插入人工审批单与 `record_audit`，因为本项目的安全承诺是**未审批绝不落库**。这是有意的偏离，不是遗漏。
20. **模拟数据必须与约束自洽**：云量改用 `gauss(0.22, 0.16)`（原 Beta(2,5) 均值 0.286，近半超过 30% 阈值导致完成率虚低）、窗口时长放宽到 20–45 min（原 8–15 min 短于最短成像时长）、订单时间范围放宽到 12–14 天（原 3–7 天落在窗口覆盖范围外）。**约束设计与数据生成必须同时调，否则测的是数据噪声不是算法。**

21. **K 去重要有可判定的指纹**：`plan_signature = 卫星 | 窗口 | 观测起止时刻`。指纹相同即同一条观测计划，落库时 upsert 而非 insert。唯一索引建在**补列之后**——`plan_signature` 是迁移新增的列，索引若写进建表脚本，旧库启动会因"列不存在"直接失败。
22. **重建窗口后要清理失效知识**：窗口重建会让旧确认计划指向不存在的窗口，这些知识必须删掉，否则知识库页面出现"指向不存在窗口的调度计划"这类脏数据。
23. **调用方指定的链路不许被路由改写**：API 层已把 `task_type` 定死（`/api/orders/run` → order，`/api/sar/analyze` → sar），`node_route` 若再用 LLM 结果覆盖，一旦 LLM 误判就会把请求送进错误的主干。现在**预设值优先**，路由只在未预设时才做意图识别。
24. **调度必须可重复执行**：订单一旦被排期，状态即变为 `scheduled/rejected`，再次运行时队列为空、页面一片空白。`/api/orders/run` 增加 `reset` 参数（把订单状态重置为 pending）与 `order_ids` 参数（只调度所选订单），前端对应「重置队列后调度」勾选项与表格多选。**演示工具连点两次就空屏，等于不可用。**

### 10.2 质量指标

约束拦截正确率、诊断/结论可追溯率、审批安全性（未审批零执行）、工作流恢复正确性、各节点耗时、演示可重复性。

> **不要在缺少测试数据时宣称"准确率 99%"或"航天级可靠性"。** 先建有标签测试集，再报准确率/召回率/误报率/漏报率。

### 10.3 安全与表达要求

**工程安全**
- 所有数据页标注"模拟数据"。
- 生成与执行严格分离；审批是执行前置条件。
- 约束校验器独立于 LLM，硬约束不可协商。
- Agent 不直接调用任何真实调度/遥控接口。
- 模型幻觉、工具失败、数据过期、权限不足均有降级路径。
- 记录模型/提示词/工具版本，可复现。

**对外表达安全（与 §1.1 证据分级纪律对应）**
- 文档与口播中每条行业事实**必须带来源**；无来源的量化指标一律不出现（T25）。
- 项目自设阈值（如 5% 辐射强度守门）**必须标明是工程验收阈值**，不得表述为行业标准。
- 审批机制的效果只表述为"操作治理与流程可追溯"，不得表述为"保证算法科学正确"。
- 影像处理与智能解译两类业务**不得混用**表述；当前不覆盖解译。
- 未接入真实测运控 / 实时轨道 / 任务下发接口前，不得表述为"已解决完整应急响应链路"。
- 与 TSLC 论文的关系只表述为"**吸收三阶段方法骨架**"，**不得表述为"复现了论文"**；论文 4.58% / 13.38% 的提升数字**不引用**（无同口径实验）。
- 订单调度为**逐单贪心**，优先级→利润映射与每星标称姿态转移时间必须标注为**项目自设的简化模型**。

> 它解决的不是'AI 算得准不准'，而是**专业工具与业务流程的协同成本**：观测任务规划和 SAR 影像处理都需要专业人员配合多个专用软件完成，规划方案要人工审核，处理过程要人工确认，处理结果要能追溯。
>
> 系统用 LangGraph 编排三条状态图：观测规划 Agent 把自然语言需求转成结构化约束，调用卫星资源查询、观测窗口查询、硬约束校验和多目标评分工具生成候选方案；SAR 分析 Agent 做元数据解析、辐射定标、质量诊断、管线横评并输出前后对比报告；订单调度链按论文的三阶段方法——指派卫星、选择时窗、确定精确观测时刻——逐单处理多订单，并用独立的分阶段校验器交叉核验，冲突订单给出可解释的拒绝理由而不是静默丢弃。
>
> 我的设计重点是**安全闭环**：规划与执行彻底分离，方案必须过独立于 LLM 的硬约束校验器，再经人工审批才允许落库，执行接口强制校验审批状态、方案版本和幂等键，所有工具调用与审计记录双表留痕，工作流支持 checkpoint 中断恢复。
>
> 项目核心不是接了一个大模型 API，而是把 LLM 限制在理解和编排，把数值计算、约束判定和执行权限交给确定性组件，形成一个**可追溯、可恢复**的业务执行闭环。"

### 12.1.1 行业背景标准表述（可直接背）

> "随着商业航天和遥感卫星星座的发展，卫星观测任务数量和数据获取能力不断提升，但卫星资源调度与遥感数据处理仍然具有较高的专业门槛。
>
> 首先，在卫星任务规划方面，需要综合考虑卫星轨道、可见时间窗口、载荷能力、姿态机动、能源和数传资源等多种约束。尤其在多卫星协同和应急任务场景下，规划问题具有较高的复杂度，传统业务流程仍然需要专业人员参与任务调整和方案审核。
>
> 其次，在遥感数据处理方面，尤其是 SAR 数据，需要专业人员根据数据特征和应用目标选择处理算法、配置参数，并通过多种质量指标验证处理结果。这使得数据处理过程具有较高的专业知识门槛。
>
> 最后，传统的专业软件通常以固定功能和固定工作流为主，用户需要分别操作不同工具完成任务规划、数据处理和结果管理，跨环节协同存在一定的自动化空间。
>
> 因此，我们设计了 StarOps 卫星遥感任务规划与智能数据处理 Agent 平台，希望利用大模型的自然语言理解和任务规划能力，将用户需求转化为可执行任务，通过工具调用整合传统卫星规划算法和 SAR 数据处理工具，同时利用确定性规则、人工审批和审计机制保证执行过程的可控性。"

### 12.3.1 深度模型选型话术（准备被追问）

> "SAR 去噪这条线上，公开的深度方案不少：MERLIN、SAR2SAR、CL-SAR-Despeckling、SAR-CAM 都有。我选 GeomaticsAndRS/sar 有三个原因：仓库自带预训练权重、不用自己训练、直接吃 TIFF，和我项目的演示数据格式对得上。MERLIN 质量更高但吃复数 SLC，SAR-CAM 没权重。
>
> 但我不打算让深度学习直接替代传统方法。我的做法是建三层基线——中值/Lee/FANS 作对照组，深度残差 CNN 作对照组，用**同一套指标**（局部方差、ENL、噪声估计、耗时）在同一张图上横评。**Agent 选的是被评测选出来的那条管线**，不是预设的。深度模型跑不起来时自动降级到经典滤波并明确标注，不伪装成功。
>
> 还有一点：SAR 深度学习的公开工作几乎全在斑点去噪上，条纹至今仍是经典频域方法主导，所以条纹检测我没硬上深度学习。
>
> 最后也是最能接上我个人工作的点——通用预训练模型保留不了 SAR 特有的纹理结构，这正是我 ScanSAR 论文里扇贝效应要解决的问题。所以这个项目的定位是：通用模型打底 + 展示出它的局限 + 指出专项算法是下一步。"

> **补充（若被追问"为什么把真实数据链路排在深度模型前面"）**："因为深度模型的价值主张必须建立在**同图同指标**的证据上，而合成模拟影像上的横评只能证明管线逻辑正确，证明不了适用于真实 SAR 产品。先把真实 GeoTIFF 读取、辐射定标、处理报告跑通，指标口径和数据链路可信之后，再引入深度模型做横评，结论才站得住。这也是我在 §4.4 把 L2 降到 P2 的原因。"

### 12.3.2 论文对齐话术（TSLC 订单驱动调度）

> "订单调度这条线，我参照的是 IEEE TGRS 2026 的一篇《A Tri-Stage LLM-Coordinated Framework for Order-Driven Scheduling of Earth Observation Satellite Tasks》。它的核心是**把 NP-Hard 的整体调度问题拆成三个顺序决策**：先指派卫星，再选有效时窗，最后定精确观测时刻，每一步配独立的分阶段约束校验，失败就由 Performance Manager 触发重规划，失败尝试记进 MS、成功计划存进 K。
>
> 我做的**匹配度分析**是逐项比的，结论是**部分匹配**——方法论同构，但工程实体不同构。论文是三元调度（卫星-任务-时间），而我原来只有二元（卫星-窗口）配对打分，连精确观测时刻都没有，更没有资源独占和姿态转移时间。这三项缺一，三阶段就退化成普通匹配。所以我先补齐了这三项前提——同星同时刻单任务、相邻任务留姿态转移余量、最短成像时长——再引入三阶段骨架。
>
> 但有几条我**明确没有引入，也不打算含糊**：论文追求**全局利润最优**，我做的是逐单贪心，优先级到利润是我自设的映射表，不代表真实商业合同的收益结构；论文是真实星座规模，我是 8 星 48 窗口 6 单的模拟规模；论文用真实的姿态转移时间矩阵，我每星只有一个标称值。**论文报告的 4.58% 和 13.38% 提升数字，我没有引用也不会复述**——那依赖同等规模实例和 CP/GA/SA/DRL 基线，我没有同口径实验就没有资格引用它。
>
> 所以我的表述是：**吸收了 TSLC 的'订单驱动 + 三阶段 + 外部校验'方法骨架，把单需求候选排序升级成多订单可解释调度**，并额外保留了论文没有的人工审批关口——调度计划生成后仍然要人工批准才能落库。这是我这个项目安全承诺决定的偏离，不是遗漏。"

> **若被追问"这不就是把论文复现了一遍吗"**："不是。复现要同规模实例、同约束数据、同基线对比。我的代码里跑的是自己的模拟数据、自己的约束阈值，指标只在 8 星 / 48 窗口 / 6 单这个规模内自洽。我把它当作**方法论对齐**，不是**实验复现**——这两个词的差别我在文档里是写死的。"

### 12.4 表达边界（必须严格守住）

- **已实现**：代码里真实跑通的功能。
- **已仿真**：在模拟数据与模拟环境中验证过的功能。
- **理论设计**：依据公开资料设计但尚未实现的能力。
- **真实应用**：需要真实数据源、硬件在环测试、独立安全验证与航天工程认证。

**本次评估新增的四条硬边界**

1. **项目自设阈值要说清楚**：5% 辐射强度守门是**本项目的工程验收阈值**，不是行业标准，也不是"航天级安全线"。
2. **审批的效力边界**：审批保证的是**操作治理与流程可追溯**，不构成对遥感算法科学正确性的证明。
3. **业务边界**：当前交付的是**遥感影像处理 + 业务流程治理**，**不含智能解译**（分类/检测/异常检测）；不要把滤波管线包装成解译能力。
4. **行业事实必须可溯源**：每条行业论断都能指出文献、专利、官方文档或标准；讲不出来源的数字**不进入口播**。

**论文对齐新增的一条硬边界**

5. **方法论对齐 ≠ 实验复现**：TSLC 论文的性能数字（4.58% / 13.38%）依赖其自建实例与 CP/GA/SA/DRL 基线，本项目**没有同口径实验**。对外只说"吸收了三阶段方法骨架"，**不说"复现了论文"**，**不引用其提升数字**。同理，优先级→利润映射、每星标称姿态转移时间都要标注为**项目自设的简化模型**。

> 全程标注"模拟数据"，不宣称真实卫星实时调度；不把普通滤波说成专利算法；不宣称任何未经测试的准确率；不引用无可溯源来源的统计数字；不宣称已解决完整应急响应链路。

## 14. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 两周做不完 | 交付残缺 | 按 §9 优先级砍；SAR 降级为简单真实功能 |

## 16. 完成判定标准

1. 面试官能从界面看到模拟卫星资源、观测窗口与两个领域 Agent。
2. 自然语言能生成结构化约束，并驱动工具编排。
3. Agent 输出的是带证据（数据来源 / 工具返回）的结构化结论，不是纯解释性文字。
4. 约束校验器能拒绝违反硬约束的方案，且拒绝原因清晰。
5. **人工批准前，任务计划绝不会被修改**（后端强制，非仅前端置灰）。
6. 批准后能执行并验证结果，失败时走升级路径。
7. 重复提交同一幂等键不产生重复副作用。
8. 工作流中断可从 checkpoint 恢复，不重复落库。
9. 全流程双表留痕，能从一份报告追溯到数据、工具、约束、审批。
10. 开发者能解释每个模块的输入、输出、职责、失败处理与安全边界。
11. **多轮修改约束时保留上下文，仅重跑受影响节点**，不从头重来。
12. **真实 GeoTIFF 上跑通完整链路**（读取 → 定标 → 指标 → 管线 → 报告），且报告含已知限制。
13. **对外表述可溯源**：每条行业事实能指出文献/标准/官方文档；项目自设阈值标明性质；业务边界（处理 vs 解译）不混淆。

> **最终定位**：以卫星观测规划 + SAR 影像处理为切入点，融合 Agent 工程、约束优化、图像处理、工具调用与安全审批的航天领域智能体原型。核心竞争力不是"发明了新的调度算法或滤波算法"，而是**把遥感领域原本分散的专业工具和业务流程封装为 Agent 可调用的能力**，让用户用自然语言发起任务，由 Agent 完成需求解析、任务编排、工具调用、结果校验与人工审批，形成一个**有数据、有工具、有约束、有审批、有审计、可追溯、可恢复**的业务执行闭环。
