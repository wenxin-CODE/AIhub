1. 基于你的背景（ERP开发 + LangChain Agent项目）和商业航天公司的岗位需求，我推荐**两个核心功能方向**，并围绕它们设计一份可在1-2周内完成演示版本的项目方案。核心思路是：**用公开的卫星遥测数据做“异常检测+归因分析”的Agent工具链，用航天技术文档做“RAG+工具调用”的多轮推理场景**。这两个方向都不需要你懂轨道力学，但能直接展示商业航天AI岗位最看重的三项能力：工具编排、领域数据处理、可演示的工程化产出。

    ## 一、推荐的核心功能方向

    ### 方向一：卫星遥测异常检测与归因 Agent（首推）

    **为什么选它**：商业航天公司（尤其是做星座运营和测运控的）最真实的AI需求之一，就是卫星遥测数据的异常发现与处置辅助。你不需要训练复杂的时序模型，而是用Agent**编排多个工具**来完成“检测→归因→建议”的闭环。这直接对应最终前沿智能体岗要求的“工具链、插件系统开发经验”，以及银河航天AI岗的“信号智能处理/在轨智能决策”方向。

    **技术亮点**：
    
    - **多工具编排**：Agent依次调用“遥测数据查询工具”“统计异常检测工具”“历史故障检索工具（RAG）”，最终输出归因报告
    - **多轮推理**：第一轮发现异常点 → 第二轮追问“这个参数在同期其他卫星上是否也异常” → 第三轮结合历史工单判断是单星故障还是批次问题
- **可验证的评估**：用公开的OPS-SAT遥测异常数据集做基准，你的Agent检测结果可以和人工标注对比，展示召回率/误报率
    -  [OPSSAT-AD - anomaly detection dataset for satellite telemetry | Zenodo](https://zenodo.org/records/15108715?utm_source=chatgpt.com) 

    **MVP范围**：预置一段OPS-SAT公开遥测数据，Agent接收“检查某时间段内某参数是否异常”的自然语言指令，调用工具链输出异常点列表+简要归因。演示时用预设的3-5个查询场景即可。

    **可扩展**：接入实时数据流、多参数关联分析、处置建议的工单自动生成。

    ### 方向二：航天技术文档智能问答与合规检查 Agent（备选/并行）

    **为什么选它**：你的个人博客RAG项目可以直接改造为这个方向，开发成本极低，但航天语境让它从“通用RAG”升级为“领域Agent”。天兵科技的AI应用工程师岗明确要求“全程主导过基于RAG框架的智能问答助手项目的落地”，这个方向直接对标。
    
    **技术亮点**：
    - **工具调用+RAG融合**：Agent不仅能检索文档回答“某型号卫星的太阳翼展开机构技术指标是什么”，还能调用“单位换算工具”“参数对比工具”进行推理
- **多轮追问**：用户问“这个指标是否满足某标准要求”时，Agent需要检索标准文档、提取条款、与给定指标做比对，分步推理
    - **展示性极强**：前端可以做成对话界面，每一步工具调用和检索来源都可视化展示

    **MVP范围**：准备10-20份公开的航天技术文档/标准摘要（可从公开的卫星用户手册、NASA技术报告摘要中摘取），构建Chroma向量库，Agent支持3类查询：指标查询、条款比对、跨文档关联。

    **可扩展**：文档版本管理、变更影响分析、自动生成合规检查报告。
    
    **建议**：以方向一为主攻，方向二作为项目内的“第二个工具场景”嵌入。这样你的Agent展示的是**多工具编排能力**（遥测检测 + 文档检索 + 数据查询），而不是单一场景的RAG，在面试中更有说服力。


    ## 二、项目需求文档
    
    ### 项目名称：AeroAgent — 航天遥测与文档智能分析 Agent
    
    ### 1. 项目定位与核心亮点
    
    **定位**：一个面向商业航天场景的轻量级Agent演示系统，展示“将LLM Agent接入航天领域数据与工具”的工程能力。项目不追求模型训练，而是聚焦**Agent编排、工具链集成、领域数据处理、前端可视化**四项能力。
    
    **应聘场景中突出的技术能力**：
    
    | 能力维度     | 展示内容                                                 | 对应岗位要求                                     |
    | ------------ | -------------------------------------------------------- | ------------------------------------------------ |
    | Agent编排    | LangGraph状态图实现多轮工具调用与条件分支                | 最终前沿“智能体开发”、SpaceX “agentic workflows” |
    | 工具链集成   | 遥测查询工具 + 异常检测工具 + RAG检索工具 + 单位换算工具 | 最终前沿“工具链、插件系统”                       |
    | 领域数据处理 | 真实卫星遥测数据集（OPS-SAT）的加载、清洗、特征提取      | 银河航天“信号智能处理”                           |
    | 前端交互     | 对话界面 + 工具调用状态可视化 + 异常标记高亮             | 商业航天AI岗普遍要求的前端展示能力               |
    
    **与ERP经历的关联话术**：面试时可说：“我在ERP开发中理解企业级系统的数据边界和权限模型，这个Agent项目里我刻意设计了工具调用的**权限分层**（遥测查询只读、处置建议需人工确认），就是把业务系统的安全思维带入了Agent设计。”
    
    ### 2. 核心功能模块
    
    #### 模块一：遥测异常检测工具链（主攻）
    
    | 要素              | 内容                                                         |
    | ----------------- | ------------------------------------------------------------ |
    | **输入**          | 自然语言查询，如“检查2024年3月1日至7日，电源系统母线电压是否出现异常” |
    | **Agent处理逻辑** | ① 解析时间范围和参数名称 → ② 调用`query_telemetry`工具从预加载的OPS-SAT数据中提取时序片段 → ③ 调用`detect_anomaly`工具（统计方法：3σ或IQR）标记异常点 → ④ 调用`search_fault_cases`工具（RAG）检索相似历史异常记录 → ⑤ 综合生成归因摘要 |
    | **输出**          | 异常点列表（时间戳+数值+偏离程度）、归因摘要（“母线电压在3月3日14:23出现单点跌落，幅度达正常范围3.2倍σ，检索到2条相似历史记录，均与载荷切换操作相关”） |
    | **MVP范围**       | 预置1颗卫星的1周遥测数据（约5000条记录），支持3个预设查询场景；异常检测用纯统计方法（无需训练模型）；归因检索使用预置的20条模拟故障记录 |
    | **可扩展**        | 支持多参数联合查询、接入实时数据流、异常检测工具替换为轻量LSTM |
    
    **数据来源**：OPS-SAT Anomaly Detection数据集（Zenodo公开，MIT许可），或ESA Anomaly Dataset中的遥测片段。选取1-2个参数、1周时间窗口即可。
    
    #### 模块二：航天文档智能问答工具（辅助，展示多工具切换）
    
    | 要素              | 内容                                                         |
    | ----------------- | ------------------------------------------------------------ |
    | **输入**          | 自然语言问题，如“某型星敏感器的姿态更新率指标是多少，是否满足某任务要求” |
    | **Agent处理逻辑** | ① 判断问题类型（指标查询 vs 条款比对）→ ② 调用`retrieve_docs`从Chroma向量库检索相关文档片段 → ③ 若涉及比对，调用`compare_values`工具进行数值比较 → ④ 生成带来源引用的回答 |
    | **输出**          | 回答文本 + 检索来源标注（文档名+页码/段落）                  |
    | **MVP范围**       | 10-15份公开航天技术文档摘要（可从NASA技术报告、卫星用户手册公开部分摘取），构建Chroma索引；支持指标查询和简单比对两类问题 |
    | **可扩展**        | 多文档版本对比、条款变更追踪、自动生成合规检查清单           |
    
    #### 模块三：Agent编排与状态可视化（贯穿模块）
    
    | 要素              | 内容                                                         |
    | ----------------- | ------------------------------------------------------------ |
    | **输入**          | 用户任意自然语言消息                                         |
    | **Agent处理逻辑** | LangGraph状态图：`agent`节点判断意图 → 条件路由到工具节点或直接回复 → 工具结果返回后回到agent节点决定下一步 → 最终生成回答。使用MemorySaver实现多轮会话记忆 |
    | **输出**          | 对话流 + 每轮的工具调用记录（工具名、参数、结果状态、耗时）  |
    | **MVP范围**       | 基于LangGraph官方ToolNode + 条件边实现，状态图节点不超过5个；前端用Streamlit或Gradio快速搭建 |
    | **可扩展**        | 加入Human-in-the-loop审批节点（对应ERP经历中的权限控制思路） |
    
    ### 3. 技术栈选型建议
    
    **核心原则**：用你已熟悉的LangChain/LangGraph生态，Python为主语言，前端用最低成本方案。所有组件都有大量公开示例可参考。
    
    | 层级      | 选型                                 | 理由                                                         |
    | --------- | ------------------------------------ | ------------------------------------------------------------ |
    | Agent框架 | **LangGraph** (Python)               | 你已有LangChain经验，LangGraph的状态图模型适合展示多轮工具编排；官方有完整示例 |
    | LLM       | **DeepSeek API** 或 **通义千问API**  | 你博客项目已用过DeepSeek；国内API访问稳定，成本低            |
    | 工具链    | LangChain `@tool` 装饰器定义4个工具  | 代码量极小，每个工具10-20行                                  |
    | 向量库    | **Chroma**（本地）                   | 你已用过，无需额外学习                                       |
    | 遥测数据  | **Pandas + NumPy** 加载CSV，统计检测 | 不需要PyTorch/TensorFlow                                     |
    | 前端      | **Streamlit**（首选）或 Gradio       | 1天内可出可交互界面；Streamlit的chat组件和状态展示很成熟     |
    | 会话记忆  | LangGraph MemorySaver                | 官方内置，无需额外开发                                       |
    | 追踪/调试 | LangSmith（可选）                    | 展示Agent调用链路，面试时可截图演示“可观测性”意识            |
    
    **开发量估算**：
    - 遥测数据加载与工具：1天
    - 文档RAG与工具：1天（复用博客项目代码）
    - LangGraph编排：1-2天
    - Streamlit前端：1天
    - 调试与演示脚本准备：2天
    - **合计约1周**，留出1周缓冲
    
    ### 4. 演示效果设计
    
    **Demo流程（面试现场，约5分钟）**：
    
    **第一幕：展示“工具编排”**（2分钟）
    - 输入：“帮我检查OPS-SAT卫星2024年3月第一周，电源系统的母线电压有没有异常”
    - 界面左侧：对话气泡显示Agent回复；右侧：工具调用时间线依次亮起——`query_telemetry`（绿色✓，耗时0.3s）→ `detect_anomaly`（绿色✓，标记3个异常点）→ `search_fault_cases`（绿色✓，检索到2条记录）
    - Agent输出：“发现3个异常点，其中3月3日14:23的跌落最显著。相似历史记录显示该时段有一次载荷切换操作，建议核查操作日志。”
    
    **第二幕：展示“多轮推理”**（1.5分钟）
    - 追问：“这3个异常点之间有关联吗？是不是同一个原因导致的？”
    - Agent调用`query_telemetry`获取相邻参数（如电流）数据 → 调用`compare_anomaly_timing`工具做时间对齐 → 回复：“3个异常点集中在14:20-14:28窗口内，母线电流同步出现波动，结合载荷切换记录，判断为同一操作事件引发的瞬态扰动，非持续性故障。”
    
    **第三幕：展示“多工具切换”**（1分钟）
    - 输入：“顺便查一下星敏感器的姿态更新率指标是多少”
    - Agent自动识别为文档查询意图，调用`retrieve_docs` → 输出答案并标注来源文档
    - 此时展示：同一个Agent，工具链从“遥测分析”无缝切换到“文档检索”，不需要用户手动切换模式
    
    **第四幕：展示“工程化细节”**（0.5分钟）
    - 展示LangSmith追踪截图或前端侧栏的“运行统计”：本轮对话调用工具4次，总耗时2.1s，Token消耗约1200
    - 一句话收尾：“这个Agent的评估我做了一个小基准：用OPS-SAT的标注异常点计算，当前检测召回率约75%，误报率约12%。后续可以把检测工具从统计方法替换为轻量模型来提升指标。”
    
    **面试展示优势**：
    - 每幕都有**可量化的输出**（异常点数量、召回率、耗时），不是“看起来能用”
    - 工具调用**可视化**让面试官直接看到Agent的推理过程，而不是黑盒对话
    - 多轮追问展示了**状态记忆**和**条件分支**，这是区分“调API”和“做Agent”的关键
    - 主动提**评估指标**，对应SpaceX岗位要求的“evaluation frameworks / observability”


    **最后一句实操建议**：先把遥测数据跑通（数据下载+Pandas加载+统计检测），这是整个项目最“航天”的部分，也是面试时最能证明你做了功课的证据。文档RAG部分复用博客代码，2天足够。Streamlit界面从LangGraph官方示例改起，不要从零写。
